# D1 账号与授权存储

账号、OAuth 和个人 MCP 令牌继续使用现有表及 API，数据归属和 scope 不变。
JDBC 保留事务；D1/Web API 通过既有参数化 QueryRunner 执行单条语句，不获取 JDBC 连接，
不发送 BEGIN/COMMIT，也不以进程锁模拟数据库事务。

实现切片及约束：

1. 读取、个人令牌创建/撤销通过适配器执行；认证用 JOIN 同时检查令牌、账号和授权状态。
2. OAuth 确认页用旧 payload 条件更新，避免并发会话覆盖绑定。先校验权限与 scope，
   再原子消费 pending/code/refresh；只有消费成功的一方可以签发后续凭据。
   已使用令牌重放（包括条件更新竞争失败）撤销整个 grant。
3. D1 多步签发失败时不返回任何令牌。已消费凭据保持已消费，需要重新授权；
   不进行自动重试或恢复已使用凭据。客户端禁用和账号版本变更直接使相关授权失效。
4. 成员创建和编辑在单条条件写入中检查操作者的当前身份与版本；密码、角色、启用状态
   和版本一并更新。owner 交接用单条 SQLite 更新同时变更两人，条件不符时两人均不变。
5. 覆盖 H2、SQLite JDBC、SQLite 自动提交的 Web API 替身；专门验证并发消费、刷新重放、
   确认页绑定竞争、签发中途失败、账号越权和 owner 交接。替身禁止获取 JDBC 连接。

网关仍使用现有 `sql`/`params` 协议，需要保留 D1 响应中的准确 `meta.changes`（或 `changes`），
条件更新以实际影响行数判定是否成功。读取应走主库，避免将认证查询改为无一致性保证的副本读取。

不新增数据库表、不改 Worker 协议、不修改线上数据库或部署配置。

D1 自动提交与 batch 事务的区别见 [Cloudflare D1 文档](https://developers.cloudflare.com/d1/worker-api/d1-database/)。
当前适配器只有单条 SQL 接口，因此本实现不假定它支持 batch。
