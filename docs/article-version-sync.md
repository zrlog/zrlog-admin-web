# 文章版本同步

文章仍直接保存、自动同步。前端不提供分支、暂存区或独立提交步骤，也不通过改写 version 重发旧正文来绕过冲突。

## 数据决策入口

`useArticleSaveCoordinator` 是编辑页面唯一的文章数据与写入协调入口。UI 提交编辑意图和逐项合并选择；协调层决定采用哪份内容、使用哪个已确认版本、是否可以写入以及何时清理本地草稿。

- `draft-sync/use-article-draft-sync` 管理本地修订号、脏状态、离线持久化和重试调度。
- `version-sync/use-article-version-sync` 是协调层内部的版本比较与合并决策单元，负责基线读取、自动合并、用户选择的有效性和恢复。它通过协调层串行提交结果，不直接另开写入通道。
- `version-sync/article-merge` 是无副作用的三方合并算法。
- `version-sync/article-version-conflict` 只呈现比较结果、输入和按钮；不读取接口、保存草稿或决定版本。
- `article-cache` 与 `article-draft-storage` 负责缓存格式、标签页隔离和关闭后的恢复；不决定覆盖远端数据。

`article-content` 不承载这些逻辑。数据层内部使用现有 React hook 和保存队列，不增加状态管理库、事件总线或新的服务端持久化模型。

## 保存与冲突契约

1. 所有保存按同一队列串行执行；发送时使用前一次请求已确认的 version。同一页面慢请求返回时，只确认其提交的本地修订，不用旧响应替换后续输入。
2. 每份本地草稿同时保存其编辑基线。version 只代表服务端确认过的版本，本地输入次数使用独立 revision。
3. 服务端仍以文章 ID 和 version 条件更新。JSON 或发布 SSE 的业务错误 `9094` 表示未接受这次写入；此时暂停写入，保留最新本地输入，重新读取远端。
4. 以基线、本地、远端作三方比较。独立字段和不同正文行的修改自动合并；同一位置的不同插入、修改或删除交由用户逐项选择或手动编辑。选择只影响对应冲突片段，保留其余双方修改。
5. 合并结果按所比较的远端 version 提交。若远端再次变化，重新比较，以已编辑的合并结果作为本地候选，不能强制覆盖。
6. 未完成的冲突选择按标签页和精确内容快照保存。远端快照变化后旧选择失效。冲突期间编辑器不可继续输入，但可查看和编辑合并结果。
7. 自动同步保留现有草稿/发布状态；显式保存草稿和发布仍表达用户的状态变更意图。

发布 SSE 在 `article` 之前的业务错误保留数字错误码，使用已有 `AdminSsePayloads.Error` DTO 和 Native Image 注册。已收到 `article` 之后的静态发布失败不当作文章写入失败。协议见 [文章发布 SSE](api/article-publish-sse.md)。

## 离线与多标签页

每个标签页在独立持久化槽中保留正文、基线和同步状态，标签页 ID 存在 sessionStorage 中以支持刷新恢复。旧版共享草稿键作为兼容读取入口保留。同步完成只清理对应副本；其他标签页的未同步内容仍存在。关闭标签页后的副本由控制台本地草稿入口恢复，合并成功后只清理仍与恢复来源相同的原副本。

这些缓存按当前后台会话隔离。浏览器清除站点数据、存储配额不足或禁用持久化时不具备外部备份能力。旧草稿缺少基线时尝试版本历史；历史不可读或本地 version 超前时停止自动判断，要求人工核对差异。

## 合并边界

正文按行比较，不对文章含义作自动判断。超大差异限制比较矩阵大小，退化为较粗的人工冲突范围，避免阻塞浏览器。仅无冲突的合并会自动提交；自动提交失败不会在相同快照上无限循环。

本改动未引入数据库事务。文章与历史记录写入之间的故障一致性仍属于后端历史持久化边界，不能由前端合并机制提供保证。

## 验证

单元测试覆盖合并算法、基线缓存、并发保存阻断、最新输入保留、重复冲突、恢复选择、发布错误码、独立标签页草稿及已发布文章的自动同步。Playwright 使用隔离 H2 后台，从实际编辑器完成多客户端、离线恢复、逐项合并和发布流程，另对桌面/移动、中英文、浅深色、缩放重排进行视觉检查。
